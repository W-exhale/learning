## 普通
- Object Header ：对象头
	- 存储在每个对象内存布局中最前端的部分
	- 类似每个Java对象的身份证，是 Java 实现多线程同步、垃圾回收和类型检查的基础设施
	- 结构
		- Mark Word（标记词）
			- 核心部分，包括
			- 哈希码（对象的身份哈希码）
			- GC分代年龄
			- 锁状态标志
				- 同步锁就改的这个
			- 线程持有的锁指针
			- ![[Pasted image 20260121152612.png]]
		- Klass Pointer（类型指针）
			- 指向该对象所属的类元数据（Class Metadata）
			- 通过这个分辨是什么类
			- 二进制代码-->2026-1-21 （嗷，原来是表示日期的代码）
		- 数组长度（Array Length）（仅限于数组对象）
	- ![[Pasted image 20260121152258.png]]
	- ![[Pasted image 20260121152448.png]]
- 指向锁记录的指针
	- 锁记录
		- 当java对象被多个线程竞争时（即加锁），JVM不直接求助操作系统的重量级锁，而是先尝试在线程自己的栈中划出一部分空间来记录这个锁信息
		- 这个空间就是锁记录
	- 改为指向锁记录的指针，表示将Object Header中的内容临时改掉指向锁记录
- 各种锁
	- 偏向锁（BiasedBiased）
		- 状态：`01`
		- 在锁上贴了线程ID，只有该线程能进去。
		- 缺点
			- 撤销偏向锁需要进入“全局安全点”（所有线程停下），成本反而很高。
	- 轻量级锁（Lightweight Locking）
		- 状态：`00`
		- 特点
			- 线程不会阻塞，而是在门口“自旋”（死循环等待），适合那些很快就能执行完的任务。
		- 实现
			- 当一个线程尝试给对象加锁时，会先尝试在自己的栈帧（Stack Frame）中创建一个名为“锁记录”（Lock Record）的空间
			- Displaced Mark Word
				- 线程将对象头中的Mark Word 复制一份到该锁记录中
				- 该操作称为Displaced Mark Word
			- CAS替换
				- 线程尝试使用CAS（原子操作）将对象头中的Mark Word替换成一个指向自己锁记录的指针
				- 指向Lock Record的对象头存了一个地址，指向锁记录
				- 锁标志位会变成00（表示轻量级锁）
		- 在CPU内部就能完成，速度很快
	- 重量级锁（Heavyweight）
		- 状态：`10`
		- 特点
			- 这种状态下，对象头的哈希码、分代年龄等信息都被挪到了 `ObjectMonitor` 对象里存着，因为对象头已经塞满了“监视器指针”。
		- 向OS申请援助，从User Mode 切换到 Kernel Mode，一个十分昂贵的操作
			- 没有抢到锁的线程会被操作系统挂起（suspended），进入阻塞状态。
		- 上下文切换
			- 锁释放时，操作系统需要重新调度，将被阻塞的线程唤醒（Resumed）
		- 需要OS内核来处理
		- 实现
			- 锁指针指向一个专门的外部数据结构——ObjectMonitor（监视器对象）
				- ObjectMonitor结构![[Pasted image 20260121155649.png]]
			- A持有锁，B来抢
			- 膨胀（Inflation）
				- 锁升级为重量级
			- 入队：JVM向操作系统中申请一个Monitor。指针指向这个Monitor，B放入 `_EntryList`挂起
			- 唤醒：A执行完释放锁，OS从`_EntryList`中挑一个线程resume，重新获得锁

## 序列化
- 序列化
	- 将内存中的对象转换成可以传输或存储的格式（json）
- 反序列化
	- 将该格式还原成对象
- serialization version：序列化版本
	- 确保在序列化和反序列化的过程中，类没有发生结构性的变化
		- 即，为了保证过去我存的数据现在的我还能认出来
	- 当实现serialization接口时，Java建议显式定义一个版本号
		- JVM序列化时会将`1L`和对象一起写入字节流
		- 反序列化时会读取流中的版本号，并和当前代码中类的版本号对比
			- 如果匹配上了就恢复对象
			- 没匹配上会抛出`InvalidClassException`异常
	- 如果不显式写，JVM会自动计算一个复杂的哈希值作为版本号
		- 但是很危险，假如我只是将public改为了private，版本号就会改变

- Java的序列化机制（java.io.Serialiable）
	- 调用 `ObjectOutputStream.writeObject(obj)` 时，开始序列化
		- 递归处理该对象引用的所有其他对象
		- 如果没有实现Serializable接口，会立即抛出 `NotSerializableException`
	- 处理“对象替换”
		- 真正写入数据前，JVM检查类中是否存在`writeReplace()`方法
		- 允许类在序列化之前“偷梁换柱”
			- `LocalDateTime` 并没有直接序列化自己，而是通过 `writeReplace` 返回了一个名为 `Ser` 的代理对象。这样做是为了减少存储空间并提高安全性。
	- 处理继承关系
		- 父类实现了序列化：按层次结构正常写入
		- 未实现
			- 父类必须有一个可访问的无参构造函数
			- 父类状态不会被存入序列化流中，在反序列化时父类字段通过无参构造函数重置
	- 数据写入
		- 默认机制
			- JVM自动写入类的元数据（标志类的数据）
		- 特殊处理
			- 在类中定义 `private void writeObject`
			- 手动添加特殊字段
	- 校验指纹
		- `serialVersionUID`
		- 如果由于改动代码导致 ID 不一致，即使数据完全对得上，也会报 `InvalidClassException` 错误并停止过程
	- 反序列化与恢复
		- 对于可序列化的类，JVM 会直接通过反射或底层机制分配内存并填入数据，**不执行该类的任何构造代码**。
		- 处理父类
			- 不可序列化的父类会通过无参构造函数初始化
		- 如果类定义了 `readResolve()`，它可以用这个方法的返回值替换掉刚刚反序列化出来的对象（常用于单例模式，确保内存中只有一个实例）

- 以`LocalDateTime` 的序列化为例
	1. 调用`writeReplace()`
	2. 转换为`Ser`代理对象
	3. `Ser`对象记录一个`byte`类型的类型标识和具体的时间数值
	4. 写入流
		- 避开了`LocalDateTime`复杂的类结构，只存储最核心的数值
